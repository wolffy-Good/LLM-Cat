# AI 正在参与研发 AI：Anthropic 的新指标揭示了 Agent 监督的缺口

[Read in English](English%20Article.md)

一家 AI 实验室可以记录每一次 Agent 行动，却仍难回答最关键的问题：**监控系统能否识别真正危险的行动？** Anthropic 于 2026 年 9 月 17 日公布了一套测量思路，分别观察 AI 参与 AI 研发的程度、内部 Agent 的监督情况，以及研发算力的分配。这些数字有价值，更重要的是它们把行业需要公开什么证据的问题摆到了台面上。

以下数字均为 Anthropic 对自身系统的报告，不能直接当作经过独立验证的行业基准。Anthropic 表示计划让外部评估者接触内部流程和数据；计划中的外部评估不等于本文所有数字已经获得外部核验。[原始资料](https://www.anthropic.com/institute/measuring-pace-of-ai-development)。

## “AI 主导”究竟是什么意思

Anthropic 报告称，截至 2026 年 8 月，Claude 在其测量范围内“主导”了 26% 的 AI 研发工作，超过 90% 的工作达到“AI 协作”或更高等级。同时，Anthropic 明确表示：在测量范围内，没有任何一类研发工作已由 Claude 完全自主完成。“主导”指模型可以从高层指令出发完成任务的大部分环节，由人监督；这与无人参与地设计、测试并发布下一代模型不同。该分级沿用 Epoch AI 提出的自动化等级，再由 Anthropic 用于自身任务分类。[原始资料](https://www.anthropic.com/institute/measuring-pace-of-ai-development)。

这个指数比展示一次惊艳的编程演示更有解释力，但也不是全体研发工时的精确计时。Anthropic 从抽样的工作记录整理出约 1.5 万项细粒度任务，构建固定的任务树，给任务赋予自动化等级，再用人员时间的估计值加权。负责判断等级的也是 Claude 模型。Anthropic 报告模型与人工判断完全一致的比例为 59%，不同人工判断之间为 35%，模型与人工相差不超过一个等级的比例为 97%。这些数字说明等级边界本身存在争议，并不能替代统一方法与外部复核。固定任务清单也可能遗漏人类转向的新工作。[原始资料](https://www.anthropic.com/institute/measuring-pace-of-ai-development)。

对普通开发团队来说，关键不是“多少任务用了 AI”，而是“哪些决定可以由 AI 在无人即时确认的情况下作出”。更有用的清单应记录任务范围、可调用工具、产生外部影响的决策点、人工签核要求，以及事后能留下什么证据。如果一项重要的 Agent 工作无法复盘，自动化比例主要只是生产率数字。

## 监控覆盖率只是第一个问题

Anthropic 称，2026 年 8 月，其使用最多的内部研发与工程平台在任一时刻约有 3 万个 Agent 工作。下面的监控数字只覆盖该平台，不能外推为 Anthropic 所有 Agent 的状况。它报告该平台 Agent 的行动在执行前 100% 经过在线监控，执行后 100% 进入离线监控。在线监控在 8 月分析的逾十亿次决策中阻止了 0.002%；离线监控约每千份记录标记一到两份，每周约 50 个最高优先级标记进入人工复核。[原始资料](https://www.anthropic.com/institute/measuring-pace-of-ai-development)。

这些是监控流程的数据，不是“所有有害行为的检出率”。很低的阻止比例可能意味着 Agent 很少出错、其他控制有效、监控漏掉了问题，或几种因素同时存在。覆盖率只能说明行动是否经过监控，不能说明监控是否理解上下文、复核人员是否看到关键证据，也不能说明干预是否赶在损害发生前。

![覆盖与检出](attachments/02-oversight-funnel.svg)

*图 2：完整记录路径不等于有效检出。作者依据 Anthropic 提出的覆盖率、复核延迟与升级比例绘制概念图。*

Anthropic 提出分别报告**覆盖率、复核延迟和升级比例**。在线监控在执行前检查，受阻行动在一周内由人复核；离线监控事后阅读行动记录，标记经过多级分类器筛选后才进入人工复核。这些时间安排对应不同风险：可逆错误可以稍后调查，可能泄露敏感材料的操作则需要在执行前可靠地拦截。Anthropic 还主张报告监控对已知异常行为的检出情况，并接受独立测试。[原始资料](https://www.anthropic.com/institute/measuring-pace-of-ai-development)。

工程上，可以为 Agent 保留持续身份，将消息与原始证据关联，并区分“拟执行”“已阻止”“已执行”“已复核”四种状态。Anthropic 介绍了其内部 Agent 框架的持续身份和可交叉引用的开放通信方式。这类结构帮助事后复盘，但团队仍须用预设的失败案例测试监控是否能检出问题，以及人能否及时介入。

## 算力投入不是安全分数

第三组数字只覆盖 2026 年 7 月 13 日至 20 日这一周。Anthropic 估计，分配给 AI 研发的算力中约 6% 用于安全工作；用于“AI 驱动的 AI 研发”的算力中约 12% 用于安全工作。Anthropic 称这些是保守估计，同时承认工作分类存在判断空间、部分负载标签只是尽力标注，而且一周样本无法证明长期趋势。若安全方法效率提高，算力占比下降也可能伴随更好的效果。因此，这些比例不能被直接做成“哪家实验室更安全”的排行榜。[原始资料](https://www.anthropic.com/institute/measuring-pace-of-ai-development)。

更值得问的是：分类定义是否清晰，能否让第三方复算？Anthropic 说明它采用分类器标注负载，也提出让外部人员抽查任务和记录。若实验室之间定义不同，相似比例可能代表完全不同的投入。若定义稳定、可审计并持续报告，算力分配才能成为外界追问研发重点的一个线索。

## 开发团队现在可以做什么

先选一条影响较大的 Agent 工作流，而不是立即建设覆盖全公司的看板。列出允许的操作，并标记会产生外部影响的节点。为每次拟调用工具的行动记录 Agent 身份、任务上下文、来源引用、执行决定、时间和复核结果。随后用一小组已知错误案例测试监控，测量执行前被发现的比例及人工复核耗时。漏掉的案例与被标记的案例都应记录。固定测试集有助于观察版本变化，持续加入新案例则可避免只针对旧题优化。

对于调用多个模型的团队，统一 API 可以减少不同提供商接口的重复接入。根据其[公开产品介绍](https://supanexus.ai/en)，SupaNexus 提供兼容 OpenAI 的接口、统一 Base URL 和项目级 API Key，是可供评估的一种选择。但接口整合本身不能证明 Agent 受到有效监督；行动记录、监控测试、人工复核与任务级评估仍需单独设计。

接下来值得观察三件事。第一，如果没有公开任务定义和一致的加权方法，自动化比例很难跨机构比较。第二，“100% 经过监控”的说法会需要独立检出测试来支撑，因为记录覆盖比识别危险行为容易统计。第三，外部审阅者可能要求把 Agent 身份、通信、工具行动和人工决定连成同一条证据链。这些判断都可由未来公开报告和外部评估检验。

最后留给读者的问题是：当一家实验室说自己的 Agent 全部受到监控，什么证据能让外界区分“完整留痕”与“有效监督”？
